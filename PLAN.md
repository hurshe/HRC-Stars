# HRC STARS — план проекта

Внутренняя система Hard Rock Cafe: документы, обучение и тестирование персонала, операционные чек-листы, признание сотрудников.

Статус: **планирование**. Документ живой — дополняется по мере обсуждения.
Последнее обновление: 2026-09-14 (этапы 0–6 закрыты)

Связанные документы: [`docs/legacy-excel-model.md`](docs/legacy-excel-model.md) — разбор текущей таблицы Excel, которую система заменяет.

## 1. Зафиксированные вводные

| Параметр | Решение |
|---|---|
| Локации | Одна сейчас, сеть потом → `location_id` в схеме БД с первого дня, UI-переключатель локаций скрыт до появления второй |
| Устройства | Телефон сотрудника + десктоп менеджера + общий планшет на точке → адаптив обязателен, вход по PIN для планшета |
| Клиенты | Веб (десктоп + планшет) сразу, нативные приложения Android + iOS с push — следующим шагом. Архитектура API-first с первого дня, единое ядро для всех клиентов |
| Языки | Польский (основной) + английский. Все тексты через i18n с первого коммита, хардкод строк запрещён |
| Хостинг | Не решён → архитектура portable: всё в Docker, никаких vendor-специфичных API |
| Юрисдикция | Польша → **GDPR применяется**. Персональные данные — отдельный модуль с повышенными требованиями |
| Почта | Нужна с первого дня (приглашения сотрудников) → SMTP-провайдер обязателен |

## 2. Стек

### Ядро
- **Next.js 16.3** (App Router) + **React 19.2** + **TypeScript** (strict) — UI и API в одном репозитории
  - Ломающие изменения версии 16, которые учитываем в коде: `middleware.ts` переименован в `proxy.ts` и работает только на nodejs-рантайме; `cookies()`, `headers()`, `params`, `searchParams` стали асинхронными без исключений; Turbopack включён по умолчанию; команда `next lint` удалена
  - **Требует Node.js 20.9+**, а Prisma — 20.19+ / 22.12+ / 24+
- **PostgreSQL 16** — реляционные связи + JSONB для схем тестов и чек-листов
- **Prisma** — миграции и типизация схемы end-to-end
- **Auth.js v5** — сессии, роли; email+пароль, PIN-вход для планшета, задел под SSO

### UI
- **Tailwind CSS v4** + **shadcn/ui** — компоненты лежат в нашем репо, полный контроль над стилем
- **next-intl** — локали `pl` (default) / `en`
- **react-hook-form + Zod** — одна схема валидации на клиенте, сервере и в мобильном API
- **TanStack Table** — матрица обучения, все таблицы, экспорт
- **TipTap** — редактор документов, рецептур и вопросов тестов
- **lucide-react** — иконки · **Recharts** — графики в отчётах
- **@react-pdf/renderer** — сертификаты и экспорт отчётов в PDF

### Инфраструктура
- **Docker Compose** — app + postgres + minio + redis
- **S3-совместимое хранилище** через `@aws-sdk/client-s3` — MinIO локально, S3/R2 в проде
- **Resend** или SMTP-релей — транзакционная почта (приглашения, напоминания). Абстрагирован за интерфейсом `MailerService`, замена провайдера = один файл
- **Playwright** (e2e) + **Vitest** (юнит-тесты бизнес-логики)
- **GitHub Actions** — lint + typecheck + тесты на каждый PR

### Клиенты

| Устройство | Клиент | Когда |
|---|---|---|
| Десктоп менеджера | Веб-приложение в браузере | Этап 0 |
| Планшет на точке | То же веб-приложение, планшетная раскладка + PIN-вход | Этап 0 |
| Телефон сотрудника | Сначала адаптивный веб, затем нативное приложение | Веб — этап 0 |
| Android / iOS | **Expo (React Native)** — общий с вебом слой типов и Zod-схем, push через Expo Notifications | Этап 7 |

Отдельного desktop-приложения (Electron/Tauri) не планирую: браузер даёт ровно то же самое без второго инсталлятора и второго цикла обновлений. Если понадобится — оборачивается за день, API к тому моменту уже готов.

PWA как замена нативному приложению рассмотрена и отклонена: push на iOS работает только для установленного на домашний экран PWA и ведёт себя нестабильно, а уведомления — ключевая ценность мобильного клиента.

### Сознательно отвергнуто
- NestJS + отдельный React SPA — вдвое больше кода на том же функционале
- MongoDB — данные строго реляционные (сотрудник → позиция → тест → попытка → ответ)
- Firebase / Supabase Auth — персональные данные + vendor lock-in при нерешённом хостинге

## 3. Архитектурные принципы

1. **API-first из-за мобильных приложений.** Вся бизнес-логика живёт в сервисном слое `src/server/services/*`. Server Actions веба и REST-эндпоинты `/api/v1/*` для мобилки — две тонкие обёртки над одними и теми же функциями. Логика не дублируется, мобильное приложение не требует переписывания бэкенда.
2. **Портируемость.** Ничего, что привязывает к конкретному облаку. Развернуть на VPS = `docker compose up`.
3. **Мультитенантность с первого дня.** Каждая доменная таблица содержит `location_id`. Доступ фильтруется в сервисном слое, а не в UI.
4. **Права проверяются на сервере.** Скрытая кнопка — не защита. Каждое действие проходит проверку роли внутри сервиса, а не в компоненте.
5. **Сквозной аудит.** Изменения персональных данных, документов, результатов тестов и выдача Wild Card пишутся в `audit_log`: кто, что, когда, старое → новое.
6. **Версионирование вместо перезаписи.** Документы, тесты и чек-листы имеют версии. Результат сотрудника всегда ссылается на ту версию, которую он реально проходил.
7. **Мягкое удаление.** `deleted_at` вместо `DELETE` — кроме GDPR-запросов на стирание.
8. **i18n с нуля.** Добавить второй язык потом = переписать все компоненты.

## 4. Позиции, роли и права

Три разные сущности, которые легко смешать в одну:

- **Позиция** — должность в кафе. Определяет, какие тесты и документы обязательны
- **Роль** — уровень в иерархии и стартовый набор прав
- **Право** — конкретное разрешение (`wildcard.grant`, `employee.personal_data.view`). Набор прав у роли **редактируется в интерфейсе**, а не зашит в код

### 4.1. Позиции

| Департамент | Позиции |
|---|---|
| Управление | `GM`, `AGM`, `MANAGER`, `SUPERVISOR` |
| Front of House | `SERVER`, `BARTENDER`, `BARBACK`, `HOST`, `BUSSER` |
| Retail | `RSA` — Retail Sales Assistant |
| Kitchen | `KITCHEN MANAGER`, `KITCHEN SUPERVISOR`, `COOK`, `DISH` |
| Склад | `RECEIVING` |

У каждой позиции свой набор обязательных тестов и документов. Один человек может занимать **несколько позиций** — в текущей таблице это видно, одни и те же люди есть и в `SERVER TEST SCORES`, и в `BARTENDER TEST SCORE`.

**Тренер — не позиция, а признак сотрудника.** Из листов `Ilu trenerów` и `Trainer Ratio & Documentation` видно, что тренер — это человек на обычной должности, которому дополнительно доверено обучение. Поэтому это флаг на сотруднике плюс набор прав, а не отдельная должность.

- Включается и снимается одной кнопкой в карточке сотрудника
- Отображается **ярлыком рядом с именем**: `SERVER · TRAINER`. Ярлык виден везде, где встречается человек — в матрице обучения, в списках, в задачах, в профиле
- Если позиций несколько, ярлык встаёт после них: `SERVER · BARTENDER · TRAINER`
- Даёт права на создание тестов и материалов и на просмотр матрицы обучения

Так же и `MIT` — это программа обучения, а не должность.

`KITCHEN MANAGER` и `KITCHEN SUPERVISOR` получают те же уровни, что `MANAGER` и `SUPERVISOR`, но с **ограничением по департаменту**: работают со своей кухней, а не со всей локацией.

### 4.2. Роли и уровни

Модель прав стоит на **двух независимых осях**:
- **Уровень** — кому можно ставить задачи (только вниз) и чьи данные видно
- **Набор прав** — что роль умеет делать. Две роли могут иметь одинаковый набор прав на разных уровнях

| Уровень | Роль | Кто это |
|---|---|---|
| 100 | `SUPER_ADMIN` | IT/владелец. Локации, системные настройки, бэкапы |
| 90 | `GM` | General Manager. Всё по локации, включая настройку прав |
| 80 | `AGM` | Assistant GM. То же, что GM |
| 70 | `MANAGER` | Менеджер и Kitchen Manager. Сотрудники, персданные, документы, тесты, задачи, выдача Wild Card |
| 60 | `SUPERVISOR` | Супервайзер и Kitchen Supervisor. **Тот же набор прав, что у `MANAGER`, без исключений.** Отличие только в уровне: менеджер ставит задачу супервайзеру, обратно — нет |
| 40 | `MIT` | Гость из другого кафе HRC. Своя программа обучения, доступа к данным локации нет |
| 10 | `STAFF` | Все линейные позиции. Свой профиль, свои документы, тесты, чек-листы, задачи, баланс Wild Card |

Дополнительно: **признак «тренер»** добавляет права на создание тестов и материалов и на просмотр матрицы обучения — поверх любой роли.

### 4.3. Редактор прав

`GM` и `AGM` меняют набор прав любой роли прямо в интерфейсе, без разработчика.

- Права сгруппированы по модулям: сотрудники, персданные, документы, тесты, чек-листы, задачи, Wild Card, отчёты, настройки
- Экран — матрица «роль × право» с переключателями
- **Персональные исключения:** право выдаётся конкретному человеку, не меняя всю роль. Например, один супервайзер видит персданные, остальные нет
- Каждое изменение прав попадает в аудит: кто, когда, что включил

**Предохранители** — без них редактор прав превращается в дыру. Проверяются командой `npm run check:guards`:
- Менять права можно **строго вниз по иерархии, свою роль включительно нельзя**. Одно это правило закрывает и «выдать полномочия тому, кто выше», и «подкрутить права себе»
- Права `SUPER_ADMIN` (локации, бэкапы, стирание персданных) из интерфейса не редактируются вообще
- Запереть систему без администратора невозможно по двум причинам сразу: своя роль не редактируется, а `SUPER_ADMIN` получает полный набор прав независимо от таблицы
- Право на просмотр персональных данных помечено как чувствительное: при включении показывается предупреждение, изменение попадает в отдельный GDPR-отчёт

Открытый вопрос: нужна ли отдельная роль `HR` — доступ к персональным данным без операционки.

## 5. Модули

### A. Аутентификация и учётные записи

**Создание сотрудника менеджером:**
1. Менеджер заполняет: имя, email, позиция(и), локация, роль
2. Система создаёт учётку в статусе `INVITED` и отправляет письмо со **ссылкой-приглашением** (одноразовый токен, срок жизни 7 дней)
3. Сотрудник по ссылке задаёт себе пароль → статус `ACTIVE`
4. Менеджер видит статус приглашения и может отправить его повторно

**Замечание по безопасности:** временный пароль в письме — плохая практика (письмо остаётся в почте навсегда, пароль ходит открытым текстом). Предлагаю вместо этого ссылку-приглашение. Но сценарий «у сотрудника нет доступа к почте прямо сейчас» реален, поэтому дополнительно: менеджер может сгенерировать **одноразовый код активации**, показать его на экране и продиктовать лично. Код действует 24 часа и требует смены пароля при первом входе. Итого закрываются оба случая, и пароль нигде не хранится в открытом виде.

**Остальное:**
- Смена пароля и email в личном кабинете, восстановление пароля по почте
- **PIN-вход для планшета на точке** — короткий код для быстрого доступа к чек-листам, без доступа к персональным данным и документам
- **Гостевые учётки MIT** — менеджеры из других кафе HRC, приезжающие на обучение. Аккаунт с датой окончания, деактивируется автоматически, интерфейс по умолчанию английский
- Блокировка учётки при увольнении (данные сохраняются, вход закрыт)
- Опционально позже: 2FA для `MANAGER` и `SUPER_ADMIN`

### B. Документы и знания — четыре пространства

Разные типы контента требуют разной модели доступа, поэтому это не одна папка, а четыре раздела с общим движком хранения.

| Пространство | Содержание | Кто видит |
|---|---|---|
| **HR-документы** | Договоры, медкнижки, разрешения на работу, CV, Job Description, подписанные политики | Только сам сотрудник + `MANAGER`/`HR`. Каждый просмотр в аудите |
| **Обучение** | Материалы, привязанные к тестам и позициям | По назначению |
| **Рецептуры и туториалы** | Рецепты, техкарты, видео, стандарты подачи | Все сотрудники локации, фильтр по позиции |
| **Общая информация HRC** | История бренда, specs, корпоративные стандарты | Все сотрудники |

Общий движок для всех четырёх:
- Загрузка PDF/DOCX/изображений/видео + документы, написанные прямо в системе (TipTap)
- Версии: новая загрузка не затирает старую
- Полнотекстовый поиск (Postgres `tsvector`, польская и английская морфология)
- Назначение роли/позиции/сотруднику + трекинг «прочитано и подтверждено» с датой
- Срок действия и напоминание о пересмотре

**HR-документы дополнительно** работают как чек-лист требований по позиции (как в текущем Excel): требование → статус (`нет` / `ожидается` / `бумажный оригинал` / `скан загружен`) → файл → дата → срок годности.

Список обязательных документов для каждой позиции менеджер настраивает сам в интерфейсе — по тому же принципу, что и назначение тестов.

### C. Тесты и конструктор

- **Назначение теста задаёт его автор.** Ответственный за обучение создаёт тест и сам указывает, кому он адресован: одной позиции, нескольким сразу, роли или программе. Плюс задаёт — обязательный или добровольный, дедлайн, периодичность повторной сдачи
- Матрица «какой тест обязателен для какой позиции» **не зашита в код** — она складывается из назначений, проставленных автором. Появилась новая позиция или новый тест — настраивается в интерфейсе без разработчика
- Конструктор: один ответ, несколько, текст, соответствие, порядок, вопрос по изображению
- Банк вопросов с переиспользованием между тестами
- **Версионирование теста:** попытка ссылается на версию с её максимальным баллом. Процент считается автоматически — расхождений, как в текущей таблице, больше не будет
- Настройки: лимит времени, перемешивание, число попыток, показ правильных ответов
- **Пороги настраиваются в интерфейсе.** Проходной балл и границы цветовых зон задаются как глобальное значение по умолчанию плюс переопределение на конкретном тесте. Менять пороги может `MANAGER` и выше, в коде ничего не зашито
- При изменении порога **прошлые попытки не пересчитываются задним числом** — иначе вчера человек был аттестован, а сегодня задним числом «завален», и история поедет. Новый порог действует со дня изменения, у старых попыток сохраняется тот, по которому их оценивали
- **Способ сдачи:** онлайн в системе или офлайн на бумаге с ручным вводом балла менеджером (в текущей таблице половина результатов бумажные — переход должен быть плавным)
- Прохождение: автосохранение прогресса, устойчивость к обрыву связи
- Результат автоматически попадает в профиль сотрудника (`staff_id`) и в матрицу
- Статистика по вопросам: какой вопрос чаще всего валят → сигнал, что материал плохо объяснён
- Периодические переаттестации с датой «следующая» и напоминанием

### D. Матрица обучения — главный экран менеджера

Живая замена таблицы Excel. Строки — сотрудники, колонки — тесты и обязательные документы, ячейка — статус с автоматическим цветом.

- Фильтры: позиция, локация, статус, дата найма
- Переключение вкладок по позициям (Server / Bartender / …)
- Клик по ячейке → карточка: попытки, баллы, кто принимал, файл документа
- Подсветка проблем: просрочено, не пройдено, скоро истекает
- Экспорт в XLSX — чтобы можно было продолжать отдавать привычный формат наверх
- Итоги: процент готовности сотрудника, процент готовности команды

### E. Персональные данные (GDPR-критично)

- Карточка сотрудника: контакты, даты, документы, позиции, история
- Шифрование чувствительных полей на уровне приложения
- Доступ строго по роли + запись **каждого просмотра** в аудит
- Сроки хранения и авто-напоминание об истечении документов (медкнижка, разрешение на работу)
- Право на доступ и стирание: экспорт всех данных сотрудника одной кнопкой, физическое удаление по запросу
- Журнал согласий на обработку

### F. Чек-листы

- Шаблоны: открытие смены, закрытие, санитария, приёмка товара
- Пункты: галочка, число, текст, фото-подтверждение, подпись
- Расписание: ежедневно / по дням недели / разово; привязка к смене и позиции
- Выполнение с телефона и планшета, офлайн с последующей синхронизацией
- Незакрытые и просроченные → на дашборд менеджера

### G. Задачи

Задачи идут **вниз по иерархии**: GM/AGM ставят менеджерам и супервайзерам, менеджер и супервайзер ставят стаффу. Исполнитель отмечает выполнение.

- Задача: заголовок, описание, исполнитель (конкретный человек, роль или позиция), дедлайн, приоритет, локация
- Статусы: новая → в работе → выполнена → **принята**. Автор при создании решает, нужна ли приёмка, или закрытие исполнителем считается финальным
- При закрытии исполнитель может приложить фото или комментарий как доказательство
- **Связь с сущностями системы:** задача привязывается к сотруднику, документу, тесту или чек-листу — «догнать Анну по Food Test», «собрать подписи по Employee Handbook»
- Автозадачи по правилам: просрочен документ → задача менеджеру; новый сотрудник → «провести ориентацию»; истекает медкнижка → задача за 30 дней
- Повторяющиеся задачи (еженедельные, ежемесячные)
- Комментарии, вложения, история изменений
- Виды: список / канбан / календарь. Разделы «мои задачи» и «задачи, которые я поставил»
- Просроченное подсвечивается и у автора, и у руководителя исполнителя

### H. Wild Cards и ваучеры

Поощрение: менеджер выдаёт Wild Card за дополнительную работу или заслугу, сотрудник копит и меняет на ваучеры.

**Цикл:**
1. **Выдача.** `SUPERVISOR` и выше. Выбирает сотрудника, количество карт, указывает причину — причина обязательна
2. **Баланс.** Карты падают на аккаунт сотрудника, он видит баланс и историю начислений
3. **Заявка.** Сотрудник выбирает ваучер из каталога. Проверка, хватает ли карт. Карты **резервируются** — иначе двумя заявками подряд можно потратить один и тот же баланс дважды
4. **Подтверждение.** Менеджеру приходит уведомление, он гасит запрос. Карты списываются, ваучер становится активным. При отклонении резерв снимается и карты возвращаются
5. **Использование.** Ваучер лежит в списке активных у сотрудника, менеджер отмечает его использованным при выдаче обеда или скидки

**Счёт менеджера.** У менеджера есть свой запас карт, и он **бессрочный** — это пачка
в ящике стола, а не начисление. Пополняет запас `GM`/`AGM` отдельным правом
`wildcard.allocate`: раздавать карты может менеджер, а вот выдавать ему новые — нет.

**Срок годности — 3 месяца, и отсчёт начинается только в момент выдачи сотруднику.**
Пока карты лежат у менеджера, никакой даты у них нет вообще. Значение настраивается.
- Списываются всегда **самые старые карты первыми** — иначе на ваучер уходят свежие, а старые сгорают, и человек теряет заработанное на ровном месте
- За 2 недели до сгорания приходит уведомление: сколько карт истекает и какого числа
- Пока заявка висит на подтверждении, зарезервированные карты **не сгорают** — иначе задержка менеджера съедала бы баланс сотрудника
- В профиле видно не только «сколько карт», но и «сколько сгорит и когда»
- Счёт менеджера заводится в тот момент, когда `GM` впервые выдаёт ему пачку. Пока счёта нет, менеджер выдаёт без ограничения по запасу — строгий режим включается настройкой `wildcard.require_manager_stock`

**Каталог ваучеров** ведём сами: название, стоимость в картах, срок действия самого ваучера, лимит на человека. Примеры: lunch, breakfast, 50 % скидка на еду.

QR-коды убрал — в цепочке «сотрудник показал менеджеру, менеджер отметил» они лишние.

- Полный аудит операций: механика по сути денежная, злоупотребления должны быть видны. Отчёт «кто сколько выдал» для GM — тем важнее, что выдающих теперь больше
- Опциональный лимит выдачи на одного выдающего в месяц — настройка, по умолчанию выключена
- Связь с пинами и годовщинами (`PINY`, `ROCZNICE STAFF` из таблицы): автоначисление за стаж

### I. Программы обучения и сертификаты

- **Программа** — упорядоченный набор материалов, тестов и практических шагов с общим прогрессом
- Онбординг новичка: NHO → Brand Induction → FSS → тесты по позиции → допуск к станции
- **Программа MIT** — для приезжающих менеджеров из других кафе HRC: свой календарь, свои материалы, куратор
- **Сертификат** по завершении: PDF с именем, названием программы, датой, номером и подписью. Генерируется системой, лежит в профиле, скачивается
- Реестр выданных сертификатов с проверкой по номеру

Решения, принятые при реализации:
- **Прогресс не хранится, а вычисляется.** Шаг-документ засчитан, если участник подтвердил прочтение *текущей* версии; шаг-тест — если есть зачтённая попытка, в том числе сданная до записи на программу. Вручную отмечаются только практические шаги. Отдельные отметки разошлись бы с модулями документов и тестов при первой же новой версии документа
- **Практику подтверждает куратор или человек с правом `program.step.verify`, но не сам участник**
- **Сертификат выдаётся явным действием** — нажатие кнопки и есть подпись выдающего. Выдать сертификат самому себе нельзя. После выдачи прогресс заморожен
- **Номер вида `HRC-01-2026-0001`**: код локации, год по часовому поясу кафе, порядковый номер. Номер читаемый — его диктуют по телефону при проверке. Гонку двух одновременных выдач ловит уникальный индекс
- **PDF неизменяем** и хранится в S3. Язык сертификата — язык интерфейса получателя: гостю MIT — английский. Шрифты Inter и Oswald (лицензия OFL) лежат в `assets/fonts` и встраиваются в файл: стандартные шрифты PDF не содержат польских букв
- Записывать на программу можно только вниз по иерархии — так же, как ставить задачи
- HR-документы в программы не включаются: они личные
- Шаг-тест можно сдать прямо со страницы программы: старт теста не требует его назначения позиции
- Новая группа прав «Программы и сертификаты»: `program.view`, `program.manage`, `program.enroll`, `program.step.verify`, `certificate.issue`, `certificate.view`. У MANAGER и SUPERVISOR — все шесть, у STAFF и MIT — ни одного: своё обучение правами не регулируется

### J. Дашборд и отчёты

- Менеджеру: незакрытые чек-листы, просроченные документы, непройденные тесты, истекающие медкнижки, открытые задачи, заявки на ваучеры
- Сотруднику: что прочитать, что пройти, дедлайны, баланс Wild Card, активные ваучеры
- Экспорт в XLSX/PDF

### K. Сквозные подсистемы

Аудит-лог, уведомления (in-app → email → push в мобильном приложении), поиск, файловое хранилище, i18n, справочники (позиции, типы документов, причины выдачи Wild Card).

## 7. Дизайн-система

Реализована как **живая страница `/design-system` внутри приложения**, а не как документ:
всё, что там показано, — те же компоненты, что стоят на боевых экранах. Документ разошёлся
бы с кодом через две недели, страница разойтись не может.

### Токены
Все цвета — в `src/app/globals.css`, в компонентах произвольных значений нет.
Имена совместимы с соглашением shadcn/ui, чтобы готовые компоненты Radix подключались
без переписывания.

| | Светлая | Тёмная (основная) |
|---|---|---|
| Фон | `#ffffff` | `#0a0a0a` |
| Карточка | `#ffffff` | `#141414` |
| Текст | `#171717` | `#fafafa` |
| Фирменный красный | `#c4161c` | `#e31b23` |
| Золото (Wild Cards, награды) | `#8a6d12` | `#e0b93f` |

Красный на светлом фоне темнее, чем на тёмном: иначе не проходит по контрасту.

### Контраст
Проверяется командой `npm run check:contrast`. Скрипт **читает сам `globals.css`**,
поэтому проверка не может разойтись с реальностью. Проверяются обе темы, 23 пары.

Важное ограничение, найденное проверкой: **красный на чёрном даёт около 4:1** — этого
достаточно для заливок, рамок и крупного текста, но не для обычного текста. Красным
мелким шрифтом на тёмном фоне писать нельзя, для подписей используется `foreground`.

Границы полей ввода используют `border-strong`, а не `border`: по WCAG 1.4.11 граница
интерактивного элемента обязана давать 3:1, иначе поле сливается с фоном.

### Типографика
**Oswald** для заголовков (плотный, ближе к духу бренда), **Inter** для текста.
Оба подключены с подмножеством `latin-ext` — без него не отрисуются польские
`ą ć ę ł ń ó ś ź ż`, а польский у нас основной язык.

Ширины кнопок и колонок не подгоняются под английские подписи: польский текст
длиннее на 15–20 %.

### Логотип
Логотип Hard Rock — товарный знак. В репозитории его нет, и рисованием он не
воспроизводится. Компонент `<Logo>` подхватывает официальный файл из
`public/brand/logo.svg`; пока файла нет, показывается текстовая заглушка.

### Компоненты
`Button` (5 вариантов, 4 размера, состояния загрузки и блокировки), `Badge`
с тонами и вариантами, `Card` / `StatCard`, поля ввода `Input` / `Textarea` /
`Select` / `Field` / `FormError`, `ThemeSwitcher`, `LocaleSwitcher`, `Logo`.

Библиотека наращивается под конкретные экраны. Делать два десятка компонентов
впрок не будем: неиспользуемый компонент устаревает быстрее, чем пишется.

### Цвета статусов вычисляются, а не задаются
Пороги тестов настраиваются менеджером в интерфейсе, поэтому `toneForScore()`
считает цвет от текущих порогов. Захардкоженный маппинг разошёлся бы с вердиктом
«зачтено / не зачтено» сразу после первой правки порога.

Тач-зоны на мобильных — минимум 44 px.

*Открыто:* официальный файл логотипа; фирменный шрифт, если он лицензирован.

## 9. Открытые вопросы

**Мешают доделать проектирование:**
1. `KITCHEN MANAGER` и `KITCHEN SUPERVISOR` — работают только со своим департаментом или со всей локацией. Сейчас в плане стоит «только кухня»
2. Кто назначает признак «тренер» — `GM`/`AGM` или любой менеджер

**Важные, но не блокирующие:**
3. `BSP` и `SOHR` — расшифровки; что именно проверяется в `BSP Visual Validation` и `BSP Last Page`
4. Хостинг — своё железо или облако
5. Перечень полей персональных данных по польскому трудовому праву
6. Брендбук HRC: логотип, шрифты, цвета; шаблон сертификата MIT
7. Интеграции с существующими системами (график смен, зарплата, POS)
8. Сколько сотрудников на локацию
9. Роль `HR` — отдельная или часть `MANAGER`
10. Почтовый провайдер: свой SMTP или внешний сервис

**Решено ранее, зафиксировано:**
- Позиции — полный список в разделе 4.1
- Назначение тестов и обязательных документов позициям — настраивается в интерфейсе автором, в коде не зашито
- Тренер — ярлык поверх позиции (`SERVER · TRAINER`), а не отдельная должность
- Пороги тестов — настраиваются в интерфейсе, глобально и на уровне теста
- Wild Cards — срок годности 3 месяца, настраивается
- Права ролей — редактируются `GM` и `AGM` в интерфейсе
- `SUPERVISOR` — полностью равен `MANAGER` по правам, включая персданные
